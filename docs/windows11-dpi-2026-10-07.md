# Windows 11 ARM / DPI — 7 октября 2026

Все четыре workflow используют `windows-11-arm`: сборка, релиз,
Proton и Cloudflare diagnostics. Перед работой обязательна проверка
`Win32_OperatingSystem.ProductType == 1`, Caption Windows 11 и native ARM64.
Windows Server fallback отсутствует. Значение WindowsProductName на образе
остаётся «Windows 10 Enterprise»; `OsName` и CIM Caption показывают
**Microsoft Windows 11 Enterprise**, build **26200**. Номер ядра `10.0`
сам по себе не определяет маркетинговую версию Windows.

Существующие приложение, self-contained публикации и native harness остаются
**win-x64**. На этом runner они работают через эмуляцию x64 Windows 11.
Установлены pinned x64 .NET SDK **10.0.100** и native WebView2 Evergreen
через официальный Microsoft bootstrapper, выбирающий архитектуру устройства.
Пакеты, бизнес-логика и публичные интерфейсы не менялись.
**0.1.54** исправляет обрезание кнопок создания профиля при ограниченной высоте:
поля прокручиваются, footer с действиями остаётся внизу. Исходный прогон ниже
выполнен до этого изменения, на **0.1.53**.

## DPI fixture

Harness получил тот же **PerMonitorV2 manifest**, что production EXE.
`DpiSmoke.cs` показывает настоящие production окна: MainWindow,
создание профиля, все пять вкладок редактора, группы и подтверждение.
Проверяются масштабы **100%, 125%, 150%, 200%**, соответствующий WPF DPI,
размеры кнопок и их границы внутри окон. PNG рендерятся при измеренной
плотности пикселей. Реальный профиль с loopback-страницей остаётся открытым:
проверяются viewport, действие DOM-кнопки и сохранённый LocalStorage marker.
Для браузера сохраняются отдельные WebView2 CapturePreview PNG, поскольку
WPF RenderTargetBitmap не снимает его HWND.

Только на одноразовом runner с одним активным дисплеем fixture пробует сменить
масштаб через driver-specific DisplayConfig packets -3/-4. Это необязательный
недокументированный test probe, не production API. Исходный масштаб
восстанавливается в Dispose. При отказе драйвера реальная смена масштаба
отмечается **NotPerformed**; вместо неё отдельно проверяется доставка
**WM_DPICHANGED** настоящим HWND и реакция WPF. JSON сохраняет mode,
запрошенный процент, HWND DPI, WPF DPI, размеры PNG и CSS/DPR браузера.
Для настоящей смены масштаба обязательны подтверждение GetDpiForWindow
и согласованный browser DPR. Synthetic message не является подтверждением
физической смены масштаба Windows.

Чтобы большие масштабы помещались, fixture может временно выбрать объявленный
драйвером режим от 1920×1200 до 2560×1600 через EnumDisplaySettings и
ChangeDisplaySettings с предварительным CDS_TEST. Это разрешено только одному
активному дисплею одноразового GitHub runner. Неподдерживаемое увеличение
разрешения отмечается NotPerformed; исходное разрешение восстанавливается
после восстановления DPI. Конфигурация пользовательских экранов не меняется.

Скрипт Test-Installer теперь пишет отдельные `installer-operation-N.log`
и сообщения начала/конца операций. `Start-Process -Wait` сохраняет ожидание
всего дерева Inno; один Process.WaitForExit этого не обеспечивает, поскольку
uninstaller запускает временный дочерний EXE. Внешний таймаут шага CI остаётся
5 минут. Эти изменения относятся к тестовому скрипту, не к самому установщику.

Ручной rebuild старого version tag получает ARM setup/runtime helpers из
коммита исполняемого workflow через отдельный checkout. Бинарники продолжают
собираться из запрошенного tag; отсутствие нового helper в историческом tag
не является причиной возврата к Windows Server.

Несколько физических мониторов, перенос между ними, пользовательский mouse
hit-testing, произвольные разрешения, аппаратные драйверы и визуальная оценка
качества шрифтов на физическом дисплее остаются **NotPerformed**.
Переключение browser `--force-device-scale-factor` в остальных тестах проверяет
privacy DPR и не засчитывается как DPI Windows. Исходные сетевые и account
ограничения [приёмки 0.1.53](acceptance-report-0.1.53.md) сохраняются.
