# Контролируемая проверка WebRTC на Windows

Используйте Windows 11 x64, .NET SDK 10, Evergreen WebView2 и **отдельные синтетические профили**.
Не открывайте стенд в профиле с действующей почтовой сессией. Стенд не содержит внешних библиотек,
публичных STUN/TURN, автоматизации аккаунтов или отправки сообщений.

## Запуск

1. Создайте локально доверенный сертификат для `localhost` и `127.0.0.1`, например через mkcert.
   Храните сертификат и ключ вне репозитория. Не отключайте проверку TLS.
2. Из корня репозитория запустите:

   ```powershell
   python tests/fixture/fixture_server.py --cert C:\fixture\cert.pem --key C:\fixture\key.pem
   ```

3. Запустите Debug-сборку, чтобы использовать поддерживаемые настройки стенда:

   ```powershell
   $env:PP_FIXTURE_ORIGINS = 'https://localhost:8443;https://127.0.0.1:8444'
   $env:PP_FIXTURE_START = 'https://localhost:8443/webrtc.html?expected=Allow'
   dotnet run --project src/ProtonProfiles.App -c Debug -p:ExperimentalProxy=true
   ```

   Release-сборка игнорирует эти переменные. Не меняйте список Proton-хостов в production.
   Для матрицы Block перезапустите приложение с `?expected=Block`; настройка в URL только задаёт
   ожидаемый результат, **не меняет защиту профиля**. В редакторе профиля выберите ту же политику.

## Матрица режимов

| Настройки профиля | Что проверять |
| --- | --- |
| Allow / RuntimeDefault | Положительный контроль: создание PC, сбор ICE-кандидатов и реальная передача синтетической строки через DataChannel |
| Block / RuntimeDefault | Только блокировка API: первый скрипт, новые realms, навигации, окна, workers и разрешения |
| Allow / RestrictNonProxiedUdpExperimental | Только действие сетевого флага: **не маскировать попытки блокировкой API** |
| Block / RestrictNonProxiedUdpExperimental | Совместное действие после независимых проверок двух механизмов |

Для каждого сценария записывайте Windows/SDK/фактическую версию Runtime, ревизию настроек,
версию скрипта и профиль (синтетический псевдоним). Приложение показывает только факт регистрации,
а не зелёный статус полного покрытия. Повторите проверки после обновления Runtime.

## API и контексты

- Первый скрипт проверяется сразу при загрузке `webrtc-context.js`, до остального кода стенда.
  Проверяются попытки конструирования и неизменяемые дескрипторы стандартного, legacy и transport API;
  отдельно записывается инвентарь RTC-имён Runtime.
- Кнопка «Фреймы и workers» проверяет синхронный доступ к свежему realm, `about:blank`, `srcdoc`,
  blob, same-origin/cross-origin документы и dedicated/shared/service workers. Каждый требуемый
  дочерний отчёт должен присутствовать: отсутствующий отчёт — **Blocked**, а не Pass.
- Нажмите обе кнопки дочерних окон. Проверяйте ранний скрипт дочернего документа и синхронный
  доступ к `window.open('about:blank')`. Перезагрузите страницу и перейдите между двумя origins.
- Если обнаружен доступный RTC-конструктор вне защиты (например, worker или быстрый iframe),
  полное покрытие получает **Fail**; отсутствие worker API — **NotApplicable** для этого Runtime.
  Если host замечает нарушение, профиль закрывается. Это позднее обнаружение, а не предотвращение
  уже случившегося сетевого действия. Сохраните результаты до закрытия, если возможно.
- Ранее сохранённое разрешение камеры/микрофона должно перекрываться Block. Проверяйте отдельно
  от отсутствия устройств и системных разрешений. Для Allow аппаратные ошибки не доказывают блокировку.
- Смените политику открытого профиля A, убедитесь в ожидающей ревизии и выполните полный перезапуск.
  Старая генерация должна завершиться; UDF, сессия и независимо открытый профиль B сохраняются.

## Сеть и положительный контроль

Кнопка DataChannel соединяет два локальных peers и проверяет получение определённой синтетической строки.
По умолчанию ICE servers пусты. Это рабочая проверка локальной передачи, **не доказательство маршрута через прокси**.
В поле ICE servers можно ввести JSON для собственного STUN/TURN стенда. TURN-пароли не включаются в отчёт.
Не копируйте credentials в журналы, чат или репозиторий; очистите поле после теста.

Проверяйте отдельно STUN, TURN/UDP, TURN/TCP, TURN/TLS, IPv4, IPv6 и local-peer. Для каждого транспорта
сначала нужен успешный контроль Allow/RuntimeDefault с наблюдаемым трафиком. При недоступном оборудовании,
IPv6 или сервере отмечайте соответствующий подпункт Blocked.

Внешнее наблюдение должно охватывать все процессы данного тестового профиля с момента создания процесса,
попытки соединения при недоступном прокси, неверных credentials и отказе прокси во время сессии.
Разделяйте RTC, DNS, QUIC и прочий трафик. Сохраните захват отдельно от обычного экспорта диагностики.
Кандидаты, HTTP IP и аргументы процесса не заменяют сетевой захват.

Для удалённых peers и TURN-транспортов дополните локальную пару двумя узлами под вашим контролем и их
сигналингом; локальная пара страницы эти сценарии не подтверждает. Не подключайте публичные leak-test сайты.
Без проверенной внешней границы запрет любых прямых соединений вне прокси остаётся Blocked.

## Ошибки и совместимость

Проверьте отдельные тестовые профили, двойное открытие/закрытие, отмену инициализации, сбой создания окна,
тайм-аут выхода процесса, холодный запуск с данными и неработающим прокси. Не удаляйте UDF и не завершайте
все процессы `msedgewebview2.exe` для обхода сбоя. При внешних argument overrides экспериментальный
сетевой режим блокирует открытие; приложение не изменяет системную политику.

Unit-проверки конфликтующих JS-дескрипторов выполняются `node --test tests/webrtc-guard.test.mjs`.
Они не имитируют WebView2 и не заменяют эту матрицу. Сбой регистрации скрипта и фактические
исключения Runtime требуют Windows debugger/fault injection на синтетическом профиле.

Для регрессии v0.1.3 проверьте быстрое удаление/перезагрузку iframe во время host-readback.
Приложение должно оставаться открытым при null/ошибке/устаревшем результате; `Unavailable` и `Obsolete`
в exported diagnostics не являются Pass. Явный false из того же живого документа всё ещё закрывает
профиль. Первоначальная ошибка регистрации guard до целевой навигации остаётся блокирующей.

После синтетических тестов проверьте существующий разрешённый аккаунт: вход/2FA, inbox, чтение,
черновик, вложения, дочерние окна и повторный запуск. Не отправляйте почту и не создавайте аккаунты
для этих проверок. При отсутствии разрешённого аккаунта сценарий W17 — Blocked.
